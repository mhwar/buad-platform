# خطة تطبيق بُعد على iOS

الهدف: تطبيق iOS لمنصة بُعد (v2) يعمل على **نفس الخادم ونفس قاعدة البيانات** (Worker `buad-v2` + D1 `buad-v2` + R2 `buad-v2-files`) بلا نسخة ثانية من البيانات ولا منطق مكرر، وتنتقل إليه المميزات من الموقع على مراحل.

---

## 1. الوضع الحالي (ما يُبنى عليه)

| الطبقة | الموجود في v2 | أثره على التطبيق |
|---|---|---|
| الخادم | Hono على Cloudflare Workers، ~37 وحدة تحت `/api/*` | يبقى كما هو. التطبيق عميل ثانٍ له فقط |
| قاعدة البيانات | D1 (`buad-v2`) عبر Drizzle، 32 هجرة | لا تُمس. لا قاعدة محلية مستقلة على الجهاز |
| الملفات | R2 (`/api/assets`) | رفع الصور والمرفقات من الكاميرا يمر بنفس المسار |
| المنطق | `@buad/domain` (المال بالهللات، الضريبة، التحصيل، التسعير...) مع اختبارات مطابقة | يُستورد كما هو في التطبيق (TypeScript صرف بلا اعتماد على المتصفح) |
| الأنواع | `@buad/schema` (Zod) + `AppType` من `@buad/api/app` | نفس العميل المُنمَّط `hono/client` يعمل في التطبيق |
| الصلاحيات | `perms` في `/api/me` + `requirePerm`/`requireRW` | نفس قواعد الرؤية تلقائياً، لأنها تُطبَّق في الخادم |
| المصادقة | كوكي `HttpOnly` لمدة 12 ساعة، و`requireAuth` **يقبل `Authorization: Bearer` أصلاً** | يحتاج إضافة صغيرة في الخادم (انظر 3) |
| التنقل | سجل واحد للأقسام في `features/more/tabs.ts`، و`PHONE_CORE = home, sales, projects, finance` | نفس ترتيب تبويبات الجوال يصير شريط تبويبات التطبيق |

النتيجة: الخادم والقاعدة والمنطق جاهزة. الشغل الجديد هو **واجهة أصلية** فقط، وإضافة صغيرة في المصادقة.

## 2. القرار التقني

**الموصى به: React Native + Expo (TypeScript) داخل نفس المستودع `v2/apps/mobile`.**

لماذا:
- نفس اللغة ونفس الحزم: `@buad/domain` و`@buad/schema` و`hono/client` و`@tanstack/react-query` و`zod` و`react-hook-form` تعمل كما هي. يعني صفر تكرار لمنطق المال والضريبة.
- أي تغيير في الـ API يكسر بناء التطبيق في CI مباشرة (الأنواع مشتركة)، فلا يصير هناك فرق صامت بين الموقع والتطبيق.
- Expo EAS يبني ويرفع إلى TestFlight وApp Store من GitHub Actions بلا جهاز Mac دائم.
- تحديثات فورية (EAS Update) للتعديلات التي لا تمس الكود الأصلي، بلا انتظار مراجعة Apple.
- دعم RTL والعربية كامل (`I18nManager.forceRTL`) والخط IBM Plex Sans Arabic الحالي نفسه.

البدائل التي استُبعدت:
- **Capacitor (تغليف الموقع الحالي):** أسرع شيء، لكن Apple ترفض التطبيقات التي هي موقع مغلف (البند 4.2)، والتجربة لا تكون أصلية. يصلح فقط حلاً مؤقتاً للتوزيع الداخلي عبر TestFlight.
- **Swift/SwiftUI أصلي:** أفضل تجربة، لكنه يعني إعادة كتابة منطق المال والضريبة بلغة ثانية واختبار المطابقة مرتين، وهذا يخالف قاعدة "مصدر واحد".

## 3. التعديلات المطلوبة في الخادم (صغيرة وتُعمل أولاً)

كلها إضافات، لا تغيّر سلوك الموقع:

1. **دخول للتطبيق يعيد رمزاً بدل الكوكي:** `POST /api/auth/mobile/login` يعيد `{ accessToken, refreshToken }`.
   - `accessToken` قصير (15–60 دقيقة)، يُرسل في `Authorization: Bearer` (المسار المدعوم أصلاً في `requireAuth`).
   - `refreshToken` طويل (30 يوماً) يُخزَّن **مشفّراً** في جدول جديد `device_sessions` (معرّف الجهاز، اسمه، آخر استخدام)، ويُدوَّر عند كل تجديد.
   - `POST /api/auth/mobile/refresh` و`POST /api/auth/mobile/logout`.
   - تغيير `token_version` (تغيير كلمة المرور أو إيقاف المستخدم) يلغي جلسات الأجهزة أيضاً، كما في الموقع اليوم.
2. **صفحة "الأجهزة المتصلة"** في الإعدادات ← حسابي، مع إلغاء جهاز بعينه.
3. **تسجيل رمز الإشعارات:** `POST /api/devices/push-token` (جدول `push_tokens`)، ثم إرسال إشعارات APNs من نفس مصادر `/api/attention` و`/api/notifications` الحالية (عبر Expo Push أو APNs مباشرة من الـ Worker، مع Cron Trigger للتذكيرات اليومية).
4. **فحص نسخة التطبيق:** `GET /api/health` يعيد `minMobileVersion` لإجبار التحديث إذا تغيّر الـ API تغييراً كاسراً.
5. **تحديد معدل** لمسار دخول التطبيق مثل `LOGIN_LIMITER` الحالي.

الاختبارات تُضاف بنفس أسلوب `auth.test.ts` و`recovery.test.ts`.

## 4. هيكل المشروع

```
v2/
  apps/
    api/        ← بدون تغيير (عدا إضافات المصادقة والإشعارات)
    web/        ← بدون تغيير
    mobile/     ← جديد: Expo + expo-router
      app/(tabs)/home, sales, projects, finance, more
      src/api.ts          ← hc<AppType>(API_URL) + Bearer + تجديد تلقائي
      src/session.ts      ← نفس meQuery و useCan
      src/secure.ts       ← expo-secure-store (Keychain)
      src/ui/             ← مكونات أصلية بنفس هوية الألوان
  packages/
    domain/  schema/      ← مشتركة كما هي
    nav/                  ← جديد: نقل سجل الأقسام (labels, perms, attention) من web إلى حزمة مشتركة بلا أيقونات
```

حزمة `nav` تضمن أن أسماء الأقسام وصلاحياتها وشارات التنبيه واحدة في الموقع والتطبيق.

## 5. المراحل (نقل تدريجي)

كل مرحلة تنتهي بنسخة على **TestFlight** لفريق بُعد، ولا تُعتبر مكتملة إلا بعد مطابقة الأرقام مع الموقع على بيانات حقيقية (نفس قاعدة v2: "لا تنتقل وحدة إلا بعد اختبار مطابقة").

### المرحلة 0 — الأساس (أسبوع إلى أسبوعين)
- حساب Apple Developer (للمنظمة، باسم المؤسسة)، Bundle ID مثل `sa.buad.app`، أيقونة وشاشة بداية.
- إنشاء `apps/mobile`، ربطه بـ pnpm workspace وbiome وCI (`pnpm verify` يشمل `typecheck` و`test` للتطبيق).
- إضافات المصادقة في الخادم (القسم 3، البنود 1 و2 و5).
- شاشة الدخول، الحفظ في Keychain، Face ID لفتح التطبيق، الخروج.
- الهيكل: شريط تبويبات (مساحة العمل، المبيعات، المشاريع، المالية، المزيد) يُخفي ما لا تسمح به الصلاحيات.
- بيئتان: تجريبية (`buad-v2.<الحساب>.workers.dev`) وإنتاج (النطاق النهائي).

### المرحلة 1 — المتابعة اليومية (قراءة أولاً) (أسبوعان إلى 3)
الشيء الأكثر استخداماً على الجوال:
- **اليوم / تحتاج تدخلك** (`/api/attention`) مع الشارات.
- **مهامي** (`/api/tasks`): عرض، إنجاز، تأجيل.
- **الإشعارات** (`/api/notifications`) + الإشعارات الفورية (القسم 3، البند 3).
- **المشاريع:** القائمة، البحث، صفحة المشروع (النبض، الحالة، الأرقام الرئيسية).
- **العملاء:** القائمة وصفحة العميل وكشف الحساب (قراءة).

### المرحلة 2 — المالية والتحصيل (3 أسابيع)
- **نظرة عامة مالية** (`/api/finance`) ومركز التحكم.
- **التحصيل** (`/api/receivables`): المستحقات، المتأخر، **تسجيل استلام دفعة** مع صورة الإيصال من الكاميرا ← R2.
- **مالية المشروع:** العقد، الميزانية مقابل الفعلي، تسجيل مصروف/مشتريات بصورة الفاتورة.
- **الضريبة** (`/api/finance/vat`): عرض الإقرار وملخص الفترة.
- كل الحسابات من `@buad/domain` نفسها، ويُضاف اختبار مطابقة في التطبيق مثل `fincalc.parity.test.ts`.

### المرحلة 3 — المبيعات والعقود (3 أسابيع)
- **الفرص** (`/api/sales`, `/api/crm`): خط المبيعات، فرصة جديدة، المتابعات وتذكيراتها.
- **عروض الأسعار** (`/api/quotes`): إنشاء من المنتجات، معاينة PDF (`/api/pdf`)، مشاركة عبر قائمة iOS (واتساب، بريد).
- **المستندات والعقود** (`/api/documents`): عرض، مشاركة رابط (`shares`)، توقيع/اعتماد.
- تحويل العرض إلى مشروع.

### المرحلة 4 — مساحة العمل والإدارة (أسبوعان إلى 3)
- **الاجتماعات والقرارات** (`/api/meetings`, `/api/decisions`) مع إضافة إلى تقويم iOS.
- **الخطط** (`/api/plans`) ومتابعة الأهداف.
- **التقارير** (`/api/reports`, `year-review`) عرضاً وتصدير PDF.
- **الفريق وسجل النشاط** (للمدير).

### المرحلة 5 — ما يبقى في الموقع (أو لاحقاً)
تبقى في الموقع لأنها مهام مكتبية تحتاج شاشة كبيرة: محرر الموقع العام، بناء المنتجات والبروشور، الاستيراد، تصدير البيانات، إعدادات المالية المتقدمة. التطبيق يفتحها في المتصفح من «المزيد» عند الحاجة.

### مكاسب خاصة بالجوال (تتوزع على المراحل)
- كاميرا ومسح مستندات للإيصالات والفواتير.
- Face ID لتأكيد العمليات المالية الحساسة.
- ودجت الشاشة الرئيسية: "تحتاج تدخلك" والتحصيل المتأخر.
- Spotlight/اختصارات Siri: "مشروع جديد"، "سجّل دفعة".
- وضع بلا إنترنت للقراءة: تخزين آخر بيانات React Query على الجهاز (`persistQueryClient`)، والكتابة تحتاج اتصالاً في البداية (لتجنب تعارض الأرقام المالية).

## 6. التحقق والجودة

- **أنواع مشتركة:** أي تغيير في الـ API يكسر `typecheck` التطبيق في نفس الـ PR.
- **اختبارات:** Jest + React Native Testing Library للشاشات، واختبارات مطابقة الأرقام بنفس fixtures `tools/migrate`.
- **e2e:** Maestro على محاكي iOS في CI للمسارات الأساسية (دخول، تسجيل دفعة، إنجاز مهمة).
- **مراقبة:** Sentry للأعطال في التطبيق، وسجلات Workers الحالية للخادم.
- **إصدارات:** EAS Build من GitHub Actions ← TestFlight عند كل دمج في `main` يمس `apps/mobile`، والرفع للـ App Store يدوياً بعد الموافقة.

## 7. النشر والتوزيع

| الخيار | متى |
|---|---|
| **TestFlight** | من المرحلة 0 للفريق الداخلي (حتى 100 مختبر داخلي) |
| **App Store عام** (مع تسجيل دخول) | إذا سيُستخدم من عملاء أو جهات خارجية |
| **Apple Business Manager (Custom App)** | إذا التطبيق لموظفي بُعد فقط، يُوزَّع بخصوصية بلا ظهور في المتجر |

متطلبات Apple: سياسة خصوصية منشورة (يمكن على موقع الجهة الحالي)، حساب تجريبي للمراجعين، وصف صلاحيات الكاميرا والإشعارات بالعربية.

## 8. القرارات المطلوبة منكم قبل البدء

1. **التوزيع:** داخلي فقط (TestFlight/Custom App) أم App Store عام؟
2. **حساب Apple Developer:** للمنظمة (يحتاج رقم D-U-N-S) أم فردي؟
3. **النطاق النهائي** للـ API (التطبيق يحتاج عنواناً ثابتاً، بخلاف الموقع الذي يستدعي `/api` نسبياً).
4. **أولوية المرحلة الأولى:** المقترح هنا المتابعة اليومية ثم المالية. لو المالية والتحصيل هي الأهم، نبدّل المرحلتين 1 و2.
